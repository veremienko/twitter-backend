# Патерни проєкту

Довідник патернів, використаних у цьому проєкті: що це, де лежить у коді й навіщо.
Оновлюється разом з кодом — додав патерн, допиши сюди.

## Архітектурні

### Microservices

Домени рознесені по окремих сервісах (`auth-service`, `user-service`, `twit-service`,
`health`, `notification-service`), кожен зі своїм кодом, портом і життєвим циклом.
Сервіси не читають чужі таблиці напряму — тільки через API сервіса-власника.

### API Gateway

`services/api-gateway` — єдина точка входу. Клієнт бачить тільки порт 3000; gateway
перевіряє сесію (`requireAuth`) і проксює запити до внутрішніх сервісів (`forward`).
Внутрішні порти назовні не видно.

### Shared library

`packages/shared` (npm workspaces, `@twitter/shared`) — спільні клієнти Kafka/Redis,
назви топіків (`TOPICS`), HTTP-хелпери (`HttpError`, `sendError`, `parseBody`,
`internalAuth`) і контракти між сервісами (`NewUserSchema`). Один код — один формат.

### Database-per-service (логічно)

Postgres один, але кожен сервіс має власний журнал міграцій
(`migrations.table` у `drizzle.config.ts`: `twit_migrations` тощо) і володіє лише
своїми таблицями. Спільна фізична БД — спрощення для навчального проєкту.

## Міжсервісна комунікація

### Синхронний REST + API composition

twit-service збагачує стрічку іменами авторів через `GET /users?ids=` до
user-service (`fetchAuthorNames` у `twit.service.ts`). Запит іде **батчем** — один
на всі id, а не по одному на твіт (захист від N+1).

### Асинхронні події (pub/sub)

twit-service публікує `twit.created` у Kafka, notification-service споживає
(`notification-service/src/index.ts`). Продюсер не знає про консюмерів — нових
підписників можна додавати без змін у twit-service.

### Transactional outbox + relay

`twit-service/src/outbox/relay.ts` + таблиця `outbox`. Подія пишеться в `outbox`
у **тій самій транзакції**, що й твіт; фоновий relay раз на секунду шле
невідправлені рядки в Kafka і помічає `sent_at`. Розв'язує проблему dual write:
без outbox падіння Kafka (або сервіса між комітом і `producer.send`) втрачає подію
назавжди. Гарантія — at-least-once, тому консюмери мають бути ідемпотентними.

### Internal token

`internalAuth` middleware + заголовок `x-internal-token`: внутрішні ендпоінти
відповідають лише тому, хто знає спільний секрет (gateway та іншим сервісам).
Примітивна службова автентифікація замість повноцінного mTLS/JWT.

## Дані

### Server-side sessions

Логін (`auth-service`) кладе сесію в Redis (`session:<sid>`, TTL 7 днів) і віддає
httpOnly-cookie `sid`. Gateway на кожен запит перевіряє ключ у Redis. На відміну від
JWT, сесію можна відкликати миттєво — логаут просто видаляє ключ.

### Cache-aside + інвалідація на запис

`getTwits` спершу дивиться в Redis (`twits:all`), на промаху читає БД і кладе копію
з TTL 30с. Кожен запис, який змінює дані зі стрічки (`createTwit`, `postLike`),
робить `redis.del` — **після** коміту транзакції, інакше паралельний читач встигає
закешувати старі дані між del і commit.

### Денормалізований лічильник

Кількість лайків живе у двох місцях: таблиця `likes` (джерело правди, рядок = лайк)
і колонка `twits.likes` (готове число для швидкого читання). Колонка не містить
нової інформації — це кешований `count(*)`, збережений у рядку твіта, щоб стрічка
не рахувала лайки на кожен запит. Ціна — два представлення одного факту можуть
розійтись, тому обидва оновлюються тільки разом, в одній транзакції (`postLike`).

### ACID-транзакції

`db.transaction` у `postLike` (insert лайка + інкремент лічильника) та `createTwit`
(insert твіта + insert в outbox): або обидві операції, або жодної. Правила:
бізнес-помилка всередині — `throw` (rollback відкотить все); помилки не можна
"ковтати" всередині транзакції (Postgres після помилки переводить її в aborted);
побічні ефекти на зовнішні системи (Redis, Kafka) — після коміту, не всередині.

### Констрейнт як інваріант

Unique на `(twit_id, user_id)` у `likes`: правило "один лайк від користувача"
гарантує БД, а не код — воно виконується навіть при гонках паралельних запитів.
Порушення (Postgres код `23505`) перекладається на доменний `HttpError 409`.

### Append-only міграції

drizzle-kit: `db:generate` → `db:migrate`. Застосовані міграції не редагуються і не
видаляються — тільки нова міграція поверх. Перегенерація застосованого розсинхронізує
журнал у БД з файлами.

## Рівень коду

### Controller / Service

Контролер (`twit.controller.ts`) парсить HTTP і віддає статуси; сервіс
(`twit.service.ts`) містить бізнес-логіку і не знає про Express. Логіку можна
тестувати без HTTP-шару.

### Dependency injection через конструктор

`new TwitService(redis)`, `new AuthService(redis)` — залежності створюються один раз
у `index.ts` (composition root) і передаються всередину. Сервіс не створює свої
залежності сам, тож їх легко підмінити.

### Router-per-domain

Роути gateway розкладені по доменах у `src/routes/` (auth, health, twits) і
збираються в один `apiRouter` (`routes/index.ts`), який монтується на `/api` одним
рядком.

### Валідація на межі + fail fast

Кожен вхід проходить Zod-схему через `parseBody` (одразу `HttpError 400` з першою
проблемою). Обов'язкові env-змінні перевіряються при старті процесу
(`if (!INTERNAL_TOKEN) throw ...`) — сервіс падає одразу, а не на першому запиті.

### Централізована обробка помилок

`HttpError` несе статус, безпечний для клієнта; `sendError` віддає його як є, а все
неочікуване логує і ховає за generic 500. Помилки інфраструктури перекладаються на
доменні на межі сервісного шару (`23505` → 409 у `postLike`).

### Health check

Окремий сервіс `health` опитує Postgres/Redis/Kafka і віддає агрегований статус
через `GET /api/health`.
